3. 🔴 인수인계 §1의 전제가 하나 틀렸다

G3. 손으로 더한 기록의 시각이 항상 "지금"이고, 영원히 고칠 수 없다

  4. 잰 기록과 적은 기록을 구분하는 칸이 없다. 지금은 칸 하나 값이지만, P6 경첩으로 2·3단계(가족·소그룹 합산)를 열면 이미 쌓인 기록은 되살릴 수 없다

G4. build()의 무-assert 치환 — 정본이 바뀌면 앱이 "0분"만 표시한다

mkcandidates.py의 치환 7단계 중 assert가 있는 곳은 ③목록·④버튼 2곳뿐이다. 가장 위험한 것은 ② 시트 HTML 주입:

빈 줄 하나, 주석 한 줄, CRLF 저장 — 무엇이든 사이에 들어오면 치환이 조용히 no-op가 되고 에러도 안 난다. 그 뒤:

  4. renderHome()이 안 돌아 홈은 HTML 하드코딩 값을 그대로 보여준다 → <div class="hero" id="totalText">0분</div>

G7. 시트가 "무엇을 지우는지" 낭독기에 말하지 않는다

5. 🔴 자동검증 61건이 왜 이 모든 걸 통과시켰나 (W9 세 번째 재현)

인수인계는 "자동 검증 61건은 이미 통과했다. 즉 '작동하는가'는 답이 나왔다"고 적었다. 답이 나와 있지 않았다.

원인 ① — 스텁이 실패할 수 없는 시험을 만들었다

function newNode(id){
  return { id, textContent:'', value:'', hidden:false, ... }   // ← 모든 노드가 hidden:false
}
...
nodes.btnAdd.click();
ok('더하기 시트가 열린다', nodes.addSheet.hidden===false && nodes.backdrop.hidden===false);

실제 HTML은 <div id="addSheet" hidden>이지만 스텁은 그 초기 속성을 반영하지 않는다. 따라서 이 단언은 btnAdd가 무엇을 하든 통과한다. 나머지 더하기 검증은 전부 시트 안 버튼을 직접 눌러서 통과했다 — 사용자가 실제로 지나가는 경로는 한 번도 검증되지 않았다.

원인 ② — 검증이 W10 위반을 합격 기준으로 못박았다
